# Adversarial review of SPEC v0.2

Verdict: **FIX-THEN-SHIP**; the reduced v1 is sensible, but the revised contract still permits false receipts and destructive downloads.  
Submission gate: Bind receipts to the actual POST attempt and make interrupted journal transitions recoverable.  
Filesystem and credential gate: Protect existing destination files, specify no-follow operations, and stop persisting raw capability-bearing responses.  
Correctness gate: Fix period selection, dataset coverage, planner normalization, JSON outcomes, and the package dependency graph.  
Release gate: Amend these contracts before implementation acceptance; the owner's confirmed Canvas access remains resolved.

Reviewed on 2026-09-09 against `docs/SPEC.md` v0.2, all 51 findings in `docs/reviews/spec-v0.1-review.md`, live primary API/crate documentation, and Canvas source at [`1c9f0bb8013ed69c4f2efe11fd483025469b7e6c`][canvas-commit]. SPEC line numbers below refer to the reviewed 737-line file, SHA-256 `01532ab313dc2e0a2d2a8617ac30482fd8ea10ed305a7c391641febdfb6efbe1`. This is a specification and source review; no implementation, authenticated account operations, platform builds, filesystem attack tests, or benchmarks were performed. The owner confirmed that access works; account access is not an outstanding finding. Upstream behavior does not establish the owner's deployed feature flags.

“Resolved” means the original v1 defect was removed from this specification, sometimes by explicit deferral. It does not mean code was implemented or validated. “Partially resolved” identifies the remaining contractual gap. Appendix E was checked against its cited substantive sections, not accepted as evidence. ## keyring 4.2.0 / Rust 1.88 answer

The concrete route is **keyring exactly 4.2.0, default features disabled, feature `v1` enabled**. Default features also enable v1, but spelling the feature explicitly removes M0-c's guess. Do not enable `cli` merely because the application is a CLI. The [4.2.0 manifest][keyring-manifest] declares Rust 1.88.0 and selects these target dependencies:

| Platform | Store selected by v1 | Store feature |
|---|---|---|
| macOS | `apple-native-keyring-store`, version requirement `1` | `keychain` |
| Windows | `windows-native-keyring-store`, version requirement `1` | No extra store feature selected by keyring |
| Linux | `zbus-secret-service-keyring-store`, version requirement `1` | `crypto-rust` |

The wrapper also depends on `keyring-core` with requirement `1.0.0`. These are upstream semver requirements, not an assertion that every store resolves to patch 1.0.0. The application does not need to choose or initialize those stores itself: [v1's initializer][keyring-v1] does so. The old keyring feature names from v0.1 are not this configuration.

This establishes the source-supported configuration, **not a completed platform build**. M0-c must resolve and lock a Rust-1.88-compatible dependency graph, build the actual macOS/MSVC/musl release targets, and exercise store operations; Linux runtime access still uses the session Secret Service. Apply the actual-error mapping in R2-M03, including inspection of initialization failure through `Entry::store_status`.

## cap-std latest 3.x answer

The latest non-yanked 3.x release in the [registry checked for this review][cap-index] is **3.4.6**. It provides directory-capability confinement, including rename: [`Dir::rename`][cap-dir] takes the source relative to its receiver and the destination relative to a supplied `Dir`; use the intended destination directory handle for both sides of the temporary-file install. [The primitive][cap-rename] constrains each path to its corresponding directory capability. It replaces an existing destination; it is not a no-clobber operation.

It **does not automatically enforce the stronger no-parent-symlink promise** in §12.3. Ordinary [open options follow links][cap-open-options]. Add **cap-fs-ext 3.4.6 with its `std` feature** (enabled by default) and use [`DirExt::open_dir_nofollow`][cap-dir-ext] for each individual parent component, retaining the opened handles; one call on a multi-component path is not a rule against every parent link. Explicit no-follow final opens/metadata are needed too, using the extension APIs where appropriate.

The remaining gaps are final-path ownership/replacement races, journal/file durability, destination-root policy, Windows link/reparse coverage, and a bounded bridge from synchronous capability files to the API's asynchronous streams. All validation, reads, temporary creation, and installation must retain the intended capabilities rather than check a path and reopen it ambiently. See R2-B03, R2-M13–M14, and R2-M24. No runtime containment qualification was performed in this review.
