# Adversarial review of SPEC v0.5

Verdict: **FIX-THEN-SHIP**; one blocker remains in the new 4xx pre-commit-refusal claim (R5-B01).
Submission: Admission, owner recovery, atomic receipts and honest file matching now resolve the earlier structural defects.
Persistence: Scoped observation identity, destination-to-manifest binding and credential cleanup still need concrete corrections.
Transport and output: The upload handoff is fixed; governor ordering and a few schema/wording details remain.
Acceptance: Fix the POST classification before submission acceptance; Rolf's confirmed Canvas access remains settled.

Reviewed on 2026-09-09 against `docs/SPEC.md` v0.5, SHA-256 `2d18a6bd467705602a24396678e9d43058dd0353de3d486c60c5d0b92571fb5c`. Line references are to that file. This covers all 15 round-4 IDs and all 35 earlier IDs marked partially resolved in [round 4](spec-v0.4-review.md). Resolutions were checked in the substantive sections, not inferred from Appendix E.

This is a specification and pinned-source review. No implementation, account writes, submissions, downloads or runtime tests were performed. Only the new 4xx assertion was rechecked against Canvas source and its relevant callees; unchanged API claims are listed below. “Resolved” means the previous specification defect is addressed, not that platform or acceptance tests have passed. New MAJOR findings below each include a concrete wrong behavior; remaining wording/example issues are MINOR.

## New findings

| Severity | ID | Section | Problem | Evidence | Proposed fix |
|---|---|---|---|---|---|
| BLOCKER | R5-B01 | §12.2, L488-499; §14, L638-650 | **The new 4xx allowlist still labels an accepted attempt as not submitted.** A valid submission with an overlong optional comment can commit the attempt, then return a decodable Canvas JSON 400. The CLI records uploaded_not_submitted and advises rerunning, potentially consuming another attempt with every retry. | The pinned [controller][controller] wraps the entire submit_homework call in an ActiveRecord::RecordInvalid rescue and renders the record's errors as HTTP 400 (L325-335). The [assignment model][assignment-model] commits homework.save! in the transaction ending at L2830, then calls homework.add_comment at L2838. [add_comment][add-comment] uses submission_comments.create! (L2643-2644). The [comment model][comment-validation] validates comment length against [a 65,535-character limit][text-limit]. Thus a valid submission plus 65,536 plain comment characters reaches a post-commit validation failure; §5 permits --comment and supplies no such bound. This is a source-derived counterexample, not a live submission test. | Keep generic RecordInvalid/error-hash 400 responses outcome_unknown after dispatch. Allow definite refusal only for specifically identified pre-commit error cases, rather than any decodable body with an allowed status. A comment-length check can improve UX but cannot make every 400 a rollback guarantee. Add commit → comment validation failure → JSON 400 to acceptance, alongside the existing commit → 5xx cases; recovery must inspect history and preserve uncertainty, without the definite-failure rerun hint. |
| MAJOR | R5-M01 | §10, L375-377; §18, L688 | **field_obs does not identify a complete scoped entity.** Its proposed key can make an observation for one grading period/mode suppress the value for another, even though the value tables themselves were fixed. | L375 keys enrollment_grades by (enrollment_id, period) and course_totals by (course_id, mode), but L377 specifies only field_obs(entity_kind, entity_id, field, observed_at). Example: enrollment E, period P, score at t=30 sets the shared observation; a Q response stamped t=20 arrives next. Its score is rejected against P's clock, leaving Q absent or stale despite Q having no newer score observation. The scalar Canvas ID alone cannot distinguish these rows. The same collision exists for course totals in all/current mode. | Key observations by the complete normalized entity key, including period/mode and any future value qualifier, or explicitly define entity_id here as an encoded composite key rather than the Canvas ID. Use that same key for clock reads and value updates in one transaction. Add out-of-order P/Q and all/current fixtures; the existing single-entity partial/full fixture does not cover this. |
| MAJOR | R5-M02 | §12.3, L546, L561-575 | **A copied dest.json makes two physical destinations share one manifest but use different install mutexes.** A UUID read from a file is not proof that the current root is the one described by the manifest. | Initialization checks only identity key and uses dest_id to choose the identity-stored DB. Copy destination A's .canvas-cli directory to another destination B under the same identity: both select the same manifest, while A/install.lock and B/install.lock are independent files. Rows and pending moves written for A are then interpreted relative to B. For a concrete clobber case, B contains an unrelated same-size file at a path recorded for A, and Canvas has a newer remote revision: L565/L572 treat B's file as a local match and replace it without --force. This does not require editing the database or knowing any secret, only copying the destination metadata. | Bind dest_id to a verified physical root identity in durable identity storage and define rename versus copy/rebind behavior. Reject duplicate-ID roots or initialize a new destination identity with an empty manifest; do not silently import ownership. Coordinate manifest initialization/recovery/writes by dest_id as well as the root, so aliases cannot take independent mutexes for shared state. Test copied metadata between roots and two concurrent roots with the same UUID. |
| MAJOR | R5-M03 | §8, L272-292 | **Pending credential cleanup is not a workable retry/logout state.** Fallback activation can succeed while its unavailable keyring remains pending, but the next login/logout must complete that unavailable cleanup first. Logout also clears the state row that is supposed to retain cleanup_pending. | L272 correctly makes activation step 3 best-effort, then says login/logout complete pending cleanup first. With an unavailable keyring, that prerequisite can block every subsequent fallback-token rotation or prevent logout from first disabling the active file credential as L292 requires. Independently, L292 says clear the state row, then keep cleanup_pending on deletion failure. No disabled/tombstone row is defined: active_source only allows keyring/file, and cleanup_pending only names one store, although deletion of both former active and stray entries can fail. | Make pending cleanup retries best-effort for login; an unavailable old backend must not block installing a newly validated fallback token. On logout, first commit a disabled credential state with durable cleanup targets, then attempt deletion. Retain a tombstone or separate cleanup record capable of naming both stores; ordinary resolution must reject disabled state. Reconcile the login/logout ordering and test repeated fallback login, unavailable pending backend during logout, and two deletion failures. |
| MAJOR | R5-M04 | §11, L430; §16, L666 | **Applying an older low sample can roll the sequence comparison backward and admit a stale high sample.** The added low-sample rule fixes the old counterexample but invalidates the new higher-sample guard unless a separate monotonic watermark is kept. | Three concurrent requests suffice. Response 3 reports 100 and is applied; response 1 then reports 90 and must also be applied. The last applied sample now belongs to request 1. A delayed response 2 reporting 800 passes the literal higher-sample condition because 2 > 1, raises the estimate and can end cooldown, although response 3 had already supplied low evidence after request 2 was issued. Pre-charging, the probe timer and 350/300 headroom do not prevent this ordering bug. | Keep the maximum applied issue sequence as a separate nondecreasing watermark; accepting a lower sample must never lower it. Specify how that watermark interacts with cooldown updates and reset. Test the 3-low → 1-lower → 2-high arrival order, in addition to one delayed high or low sample alone. The estimate remains a heuristic, as §15 already states. |
| MINOR | R5-N01 | §12.3, L563-575 | **The replacement-crash outcome is stated unconditionally even though normal matching is size-only.** The move marker/hash fix is sound for the earlier different-bytes target case; this remaining claim is inaccurate. | After replacing a file with different bytes of the same size and dying before manifest commit, the old row remains. With --verify off, L565 still calls the local file a match. A changed remote tuple therefore selects install/replace at L572, not modified as L563 promises. This is not a new demand to hash every ordinary rerun: it is a contradiction between the advertised recovery result and the accepted default policy. | Say that an interrupted replacement is modified only when the selected comparison detects a difference; otherwise it follows the ordinary clobber table and may redownload. If unconditional interrupted-replacement detection is required, add an install marker instead. Adjust the same-size crash acceptance case to the chosen policy. |
| MINOR | R5-N02 | §12.2, L490, L507-536; Appendix D, L792-814 | **Finish the small schema/wording edges around the new receipt and candidate types.** The core provenance and nullable-digest fixes are present. | L507 selects only entries whose body hash equals sent_sha256, then says sanitization can make content_matches=false; under that filter a selected entry necessarily matches. Candidate also requires attachment_ids, which the prose server_match literal omits. receipts export accepts --json when --out is a path, but receipts@1 lists list/show/acknowledge without an export payload. The example Posted/Readback omits the required submitted_at_local siblings. The prose readback record uses the same allowlist as Posted while the public Readback type is a subset; distinguish stored record from output projection. The first successful transition to matched also needs an explicit envelope outcome/exit choice. | Keep the exact-content filter and use server_match=null when none qualifies, or explicitly define a separately labeled nonmatching candidate; never print matching-attempt text for a nonmatch. Populate attachment_ids=[] for text/URL candidates. Define the export JSON result and matched outcome/exit, make the stored/public readback relationship explicit, and align example timestamp siblings. These require no change to the honest unproven-attribution policy. |
| MINOR | R5-N03 | §§5-6, 10, 12.1, 13; L176-189, L377, L447, L622 | **A few general rules still use the superseded terminology or omit the new specific exception.** The specific v0.5 rules are sufficient to establish the intended behavior, so these are alignment nits. | Class B never connects, but the general resolver still says online cache misses fetch; only open spells out its local name-miss result. A stale needed detail field says refresh the full dataset even though the same paragraph says can_submit comes only from the single-assignment endpoint. Todo and Appendix C still say field-group freshness, and architecture still says both databases after §10 adds manifest databases. | State the class-B cache-only resolver failure rule for alias/receipt filters as well as open; direct any needed can_submit refresh to the single-assignment endpoint, preserving unknown/stale when unavailable. Replace field-group/both-databases shorthand with the current per-field and three-kind contracts. Keep the existing owners and lane graph. |
