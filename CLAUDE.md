# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`canvas-cli` is a Rust workspace that builds one binary, `canvas`: a student-only
command-line client for Canvas LMS. `docs/SPEC.md` (about 2,200 lines) is the
contract. Section numbers in code comments, commit messages, and task briefs
(`§7`, `§14`, `§19 item 50`) refer to it. Read the cited section before changing
the behaviour it governs. README.md is the short version and is tested against
the binary (see "Docs that tests enforce").

## Commands

```sh
just check            # fmt + clippy + test + deny, the four gates CI runs
just fmt              # cargo fmt --all --check
just lint             # cargo clippy --all-targets --all-features -- -D warnings
just test             # cargo nextest run --all-features (falls back to cargo test)
just deny             # cargo deny check
just msrv             # cargo +1.88 check --workspace --all-targets (fifth gate)
cargo build --release # binary at target/release/canvas
```

Clippy runs with `pedantic` at `warn` and CI uses `-D warnings`, so a pedantic
lint is a build failure. `unsafe_code` is forbidden. Every dependency is pinned
with `=`; do not loosen a pin or add one without checking SPEC Appendix A.

Run one test or one binary with nextest filters:

```sh
cargo nextest run --all-features -E 'test(replace_rebinds_profile)'
cargo nextest run --all-features -E 'binary(e2e)'
cargo nextest run --all-features -E 'binary(e2e) and test(exit_9)'
cargo nextest run --all-features -p canvas-core -E 'test(journal)'
```

Extension tests are plain Node, no install step:

```sh
cd extension && npm test
```

Workspace automation lives in `xtask` and is spelled `cargo xtask <task>`:

```sh
cargo xtask bench --mcp --runs 3           # rewrites docs/bench.md, checks SPEC §13 targets
cargo xtask dist-assets --out target/dist-assets   # man pages and completions
cargo xtask sanitize --in DIR --out DIR    # redact a recorded fixture set
```

`docs/release.md` is the release runbook. `release.yml` is generated by
`dist generate`; do not hand-edit it.

## Snapshot tests

The end-to-end suite (`crates/canvas-cli/tests/e2e/`) runs the built binary
against a `wiremock` Canvas and snapshots stdout, stderr, and the exit code
with `insta`. Snapshots live in `crates/canvas-cli/tests/e2e/snapshots/`.

`cargo-insta` is not installed on this machine. To accept snapshot changes:

```sh
INSTA_UPDATE=always INSTA_FORCE_UPDATE=1 cargo nextest run --all-features -E 'binary(e2e)'
cargo nextest run --all-features -E 'binary(e2e)'   # second run, no INSTA_* vars
```

Read the diff before the first run. A snapshot that differs between the two
runs carries an unpinned value. Add that value to `VOLATILE_KEYS`,
`VOLATILE_NUMBER_KEYS`, or `E2e::mask` in `harness.rs` instead of accepting it.
`docs/testing.md` has the full procedure and the fixture-adding steps.

The harness fixes `COLUMNS=100`, `--color never`, `TZ=America/New_York`, and
`CANVAS_NOW=2026-09-09T17:05:12Z`. The `CANVAS_TEST_*` and `CANVAS_NOW`
variables only work in debug builds.

## Architecture

Three crates plus `xtask`, with a strict dependency direction:

- `crates/canvas-api` is the HTTP client. It owns `Secret` (a token that never
  prints), the request governor (rate limiting from Canvas headers), pagination,
  redaction, upload and download transport, and all API models. It knows
  nothing about disk, config, or output.
- `crates/canvas-core` is the domain. It owns every SQLite database (cache,
  state, download manifests), all locks, the `Dataset` trait and `sync` refresh
  logic, name resolution, the `todo` merge, the submission journal, receipts,
  operation plans and approval, the browser-companion broker, and the blocking
  I/O bridge (`io`) that runs cap-std and credential-store work on
  `spawn_blocking` with bounded channels.
- `crates/canvas-cli` is the binary (package name `canvas-lms-cli`, bin name
  `canvas`). It owns the clap command tree, identity selection, config,
  credentials, renderers, the JSON envelope, the schema registry, and the MCP
  server. The clap definition lives in the library target (`cli.rs`) so
  `xtask dist-assets` can build man pages from the same tree the binary parses.

Runtime is `tokio` `current_thread` plus the blocking pool. `Store` opens
without a network client. `Session` adds a `Client` lazily, only when a command
needs the network.

### Concepts that cross many files

**Identity.** Every cache row, alias, journal, receipt, and download is bound to
an identity = (canonical origin, Canvas user ID). The identity key names the
data directory under `~/.local/share/canvas-cli/<key>/`. Tests set
`CANVAS_CONFIG_DIR` and `CANVAS_DATA_DIR` to isolate.

**Command classes** (SPEC §5). Every command is class A (identity-free, local),
B (identity-bound, local), C (cache-backed read), or D (network-required). The
class decides identity selection and the `--offline` rule. A new command must
be placed in one class.

**The JSON envelope** (SPEC §7). Every data command prints exactly one JSON
document with `--json`. The envelope keys are fixed. `schema` is
`canvas-cli/<command>@<n>`; adding a field keeps `n`, removing or changing one
bumps it. IDs are decimal strings, timestamps RFC 3339 UTC, `null` means
unknown. stdout carries data only; progress and logs go to stderr.

**The schema registry** (`crates/canvas-cli/src/output/registry.rs`). Each
schema has a `SCHEMA_*` constant, a Rust result type, and a fixture JSON in
`src/output/schemas/`. `canvas schema <command>` derives JSON Schema from the
Rust types with `schemars`, and `getclitools` on the MCP surface is built from
the same registry. Adding a `result` payload means: a fixture file, an entry in
`all_schemas()`, and a row in `SHAPES` in `tests/e2e/schema.rs`. The schema
conformance test checks every JSON snapshot against its fixture for key set,
nullability, and sort order.

**Exit codes** (SPEC §14). Codes 0 through 13 have fixed meanings. Aborts use
the `error@1` schema; completed commands with non-success outcomes use their
own schema with `outcome` set. Exit 8 refusals carry a machine-readable
`details.reason`. The abort precedence is 2, 3, 13, 4, 5, 6, 7; the completed
order is 9 > 10 > 8 > 12 > 11 > 0. `tests/e2e/exits.rs` has one test per code.

**Datasets and observations** (SPEC §10). The cache stores per-field
observations with timestamps, not whole rows, so a partial fetch and a full
fetch can arrive out of order and the newer field wins. Mutation epochs abort a
refresh that raced a write.

**Journals and plans.** `submit` (§12.2), discussion and inbox writes (§25),
and agent-driven operations (§20) all follow the same discipline: admission
lock, insert, an owner lock, guarded `UPDATE ... WHERE state = ?` transitions,
and an owner-absent recovery table. Crash tests (`*/crash_tests.rs`) kill the
process after each phase. Do not add a state transition without a guard.

**Migrations.** `crates/canvas-core/src/store/migrate.rs` holds numbered
batches keyed on `PRAGMA user_version`, separately for cache and state. The
table at the top of that file is the migration list. Download manifests have
their own list (`dl_0001`).

**The MCP surface** (SPEC §21). `canvas mcp` serves exactly one tool,
`getclitools`, which returns the command reference and performs nothing. This
was an explicit owner decision on 2026-09-10 ("mcp is just the one tool for the
cli thats it"). Do not add tools, resources, or subscriptions.

**The browser companion** (SPEC §24). `extension/` is a Chrome extension with
no build step. `canvas bridge host` is the native-messaging host; the broker in
`canvas-core::bridge` holds the attachment. The extension is shipped unpacked
inside the release archives.

## Docs that tests enforce

These files are checked by tests, so an edit to one side needs the other:

- README `## Commands` table must match the clap command tree exactly
  (`tests/readme.rs`). A new command needs a row; a removed one loses its row.
- `skill/canvas-cli/*.md` must route every workflow through `canvas` commands
  and must not name any removed MCP tool (`tests/skill.rs`).
- `docs/testing.md` table between `<!-- spec-16-row-3 -->` markers must name
  tests that exist (`tests/e2e/selection.rs`).
- Shell completions printed by the binary must equal what `dist` writes
  (`tests/dist.rs`).

## Workflow conventions

Work is organised as packages named `M<n>-<letter>` (M0-a through M9-b). Each
has a brief in `tasks/`, and each merged package has a review in
`docs/reviews/code-<PACKAGE>.md`. A brief cites the SPEC sections it
implements. Post-v1 packages are listed in `docs/agent-ux/REPORT.md` §4.

Commit messages are conventional commits and drive the changelog through
`release-plz`: `feat:` and `fix:` land in CHANGELOG.md, `review(<PACKAGE>):`
and `chore:` are skipped. A `!` marks a breaking change. Do not hand-edit
released changelog sections.

SPEC §19 is the owner's open-question ledger. When an implementation deviates
from the SPEC or resolves an ambiguity, record it as a numbered item there
rather than silently diverging.

`docs/bench.md` is generated by `cargo xtask bench`. Do not edit it by hand.

Fixtures in `crates/canvas-api/tests/fixtures/` must be sanitized. Never commit
a recording from a real account without running `cargo xtask sanitize` first.
